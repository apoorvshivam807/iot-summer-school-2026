### Q2) A smart factory contains 500 sensors distributed across a 2 km area. Compare Wi-Fi, Bluetooth, LoRa, and MQTT-based communication. Which protocol or combination of protocols would you choose and why?

**Answer:**

* **Comparison of Protocols:** * **Wi-Fi** offers high data throughput but consumes significant power and generally lacks the range to reliably cover a distributed 2 km factory area. 
    * **Bluetooth** is highly power-efficient but is strictly short-range, making it entirely unsuitable for a large factory layout. 
    * **LoRa (Long Range)** is designed specifically for transmitting small packets of data over long distances (several kilometers) with minimal power consumption, making it ideal for distributed sensor networks. 
    * **MQTT** is a lightweight software messaging protocol optimized for high-latency or unreliable networks, rather than a physical wireless standard.
* **Optimal Combination:** A combination of LoRa and MQTT is the best solution for 500 sensors across a 2 km area. The 500 distributed sensors should communicate via LoRa to a central LoRaWAN gateway situated in the factory. The gateway would then translate these signals and publish the data payloads to the factory's central server using the MQTT protocol. This provides robust long-range coverage while maintaining a standardized, organized data stream.

### Q3) A temperature sensor suddenly starts showing impossible values (e.g., –120°C or 300°C). How you would determine whether the problem lies in the sensor, wiring, power supply, ADC, or software.

**Answer:**

To determine why a temperature sensor is displaying impossible values like -120°C or 300°C, I should isolate the components systematically:

* **Wiring:** Use a multimeter to check for floating pins or disconnected wires, as a broken signal or ground wire frequently forces readings to extreme maximums or minimums.
* **Power Supply:** Measure the input voltage at the sensor pins; voltage drops or electrical noise can corrupt the internal logic of digital sensors.
* **Sensor Hardware:** Swap the malfunctioning sensor with a known working identical model to determine if the hardware itself has failed.
* **ADC (Analog-to-Digital Converter):** Input a known, stable voltage from a voltage divider into the controller's ADC pin to verify if the controller is registering voltages correctly.
* **Software:** Print the raw digital output or raw ADC values to the serial monitor before any mathematical conversion takes place. If the raw data is completely normal but the output displays as an impossible extreme, the conversion formula or variable data type in the code is incorrect.

2.  **Robust Authentication:** Replace hardcoded default passwords with unique cryptographic tokens (like JSON Web Tokens) or API keys for device access.

4.  **Network Segmentation:** Isolate IoT devices on a restricted guest VLAN so compromised devices cannot access the main secure network.
5.  **Disable Unused Ports:** Close unnecessary network services (such as Telnet or open HTTP servers) to reduce the device's attack surface.

### Q10) Your ESP32 must simultaneously interface with a DHT11 sensor, an ultrasonic sensor, an OLED display, a relay module, and a soil moisture sensor. What hardware or software conflicts could occur, and how would you solve them?

**Answer:**

* **Conflicts:** Interfacing these components simultaneously can cause resource contention. Hardware conflicts may manifest as power brownouts if the relay and OLED draw more current than the 3.3V pin can supply, causing the microcontroller to reset. Software conflicts primarily involve blocking code; reading the DHT11 requires precise timing delays, which can block the CPU and cause it to miss ultrasonic echo pulses or lag the OLED display.
* **Solutions:** To solve hardware conflicts, the high-draw components (relay and OLED) should be powered directly from an external 5V power supply rather than the ESP32's internal regulator (ensuring a common ground is shared). To solve software conflicts, eliminate blocking `delay()` functions entirely and transition to non-blocking timing using `millis()` or an RTOS (Real-Time Operating System). Assigning strictly timed sensor reads to one core and display updates to the other core of the ESP32 will prevent timing collisions.

### Q14) Compare polling and interrupt-based programming in embedded systems. In which situations would interrupts significantly improve the performance of an IoT device?

**Answer:**

* **Comparison:** Polling is a programming method where the microcontroller continuously checks the status of a pin or sensor in a continuous loop, which monopolizes processing time and consumes heavy power. Interrupt-based programming allows the main loop to ignore the sensor entirely; the hardware triggers an event only when a state change occurs, forcing the CPU to pause its current task, run an Interrupt Service Routine (ISR), and then resume.
* **Performance Improvements:** Interrupts significantly improve performance in battery-operated IoT devices by allowing the microcontroller to remain in an ultra-low power deep sleep state, waking only when an external trigger (like a button press or motion detection) fires. They also guarantee near-instantaneous response times for critical events (like a safety cutoff switch) that a busy polling loop might miss.
